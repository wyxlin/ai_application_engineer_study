## What I studied

### What is RAG?
RAG (Retrieval-Augmented Generation) is the process of retrieving relevant data and using it to generate a grounded answer. We use an embedding model to convert text into vectors, store them in a vector database (like FAISS), and retrieve the most semantically similar content to pass as context to the LLM.

### The four steps
```
1. RETRIEVE  — FAISS search → top N relevant JDs
2. AUGMENT   — inject retrieved JDs into the prompt as context
3. GENERATE  — LLM reads context + resume → grounded answer
4. OUTPUT    — answer references specific retrieved content
```

### Without RAG vs With RAG
- **Without RAG**: LLM answers from general training knowledge — generic, not grounded
- **With RAG**: LLM answers from retrieved real data — specific, grounded, accurate

## What I built

### Full RAG pipeline (`projects/rag/rag_test.py`)
```python
# Step 1: Build or load FAISS index
if INDEX_DIR.exists():
    vector_store = FAISS.load_local(INDEX_DIR, embeddings, allow_dangerous_deserialization=True)
else:
    vector_store = FAISS.from_texts(job_descriptions, embeddings)
    vector_store.save_local(INDEX_DIR)

# Step 2: Retrieve
retrieved_jds = vector_store.similarity_search(resume, k=3)
context = "\n".join([f"- {doc.page_content}" for doc in retrieved_jds])

# Step 3: Augment + Generate
chain = prompt | llm
result = chain.invoke({"context": context, "resume": resume})
```

### Key improvements
- Used `Path` for cross-platform index directory handling
- Added existence check — embed once, load on subsequent runs

---

## Key lessons

1. RAG = retrieval + augmentation + generation
2. "Grounded" means the answer is based on retrieved data, not model memory
3. The LLM only sees the retrieved subset — not the full database
4. Persist the FAISS index to avoid re-embedding on every run
