## What I studied

### What is an agent?
An agent lets the LLM decide what to do next — which tools to call, in what order, and when to stop. Unlike a fixed pipeline where you hardcode every step, an agent is dynamic.

### Agent vs Workflow
| Workflow | Agent |
|---|---|
| Steps hardcoded by you | Steps decided by LLM |
| Predictable | Flexible |
| Use for fixed processes | Use for open-ended tasks |

### Tools
Functions the LLM can choose to call:
```python
@tool
def search_jobs(role: str, location: str) -> str:
    """Search for job listings by role and location."""
    ...
```
The docstring is critical — the LLM reads it to decide when to call the tool.

### Guardrails via system prompt
```python
system_prompt = """
Allowed actions: search_jobs, evaluate_fit, get_resume
Rules:
- Always retrieve resume before evaluating fit
- Evaluate ALL jobs returned by search
- Maximum 5 tool calls per response
- Always end with a clear recommendation
"""
agent = create_react_agent(llm, tools=tools, prompt=system_prompt)
```

### Agent architecture for job-search assistant
```
User request
    ↓
Agent (gpt-4o)
    ├── get_resume()      → candidate profile
    ├── search_jobs()     → list of JDs
    └── evaluate_fit()    → fit score per JD (called N times)
    ↓
Final recommendation
```

---

## Key lessons

1. **Docstrings are the tool interface** — the LLM decides when to call a tool based on its description
2. **Guardrails live in the system prompt** — define allowed actions, rules, and stopping conditions explicitly
3. **Not everything should be an agent** — use workflows for fixed processes, agents for dynamic ones
4. **`prompt` parameter** in LangGraph 1.x `create_react_agent` injects the system prompt
